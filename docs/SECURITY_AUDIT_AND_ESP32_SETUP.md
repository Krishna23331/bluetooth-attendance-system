# PACBAS — Comprehensive Security Vulnerability Audit & ESP32 Setup Guide

**Target System**: Proximity-Based Anti-Cheat Bluetooth Attendance System (PACBAS)  
**Components Evaluated**: ESP32 Beacon Firmware (`PACBAS_Beacon.ino`), Android Mobile Client (`com.pacbas.attendance`), Node.js/Express Backend API (`pacbas-backend`), and the BLE/RF Physical Medium.

---

## Executive Summary

The PACBAS architecture is designed to automate classroom attendance using an ESP32 Bluetooth Low Energy (BLE) beacon and an Android companion app. While the system demonstrates a functional proximity pipeline, an exhaustive security audit reveals **critical architectural vulnerabilities** that allow trivial attendance spoofing, replay attacks, beacon cloning, credential-less submissions, and network eavesdropping.

The most critical finding is the **"Proximity Validation Fallacy"**: while the system purports to perform server-side distance re-validation, the distance calculation is entirely dependent on client-reported RSSI data submitted in a plain JSON payload. Any user on the network can submit arbitrary RSSI numbers (e.g. `-50 dBm`) and force the server to record them as "present", completely bypassing the physical beacon.

### Detailed Vulnerability Breakdown

#### VULN-01: Untrusted Client-Reported Proximity (The Proximity Fallacy)
- **Severity**: **CRITICAL** (CVSS: 9.8)
- **Affected File**: `backend/routes/checkin.js` (lines 13–29), `android-app/.../ApiClient.kt`
- **Technical Analysis**:
  `POST /checkin` accepts a JSON body:
  ```json
  {
    "studentId": "2024CS001",
    "beaconUuid": "8ec76ea3-6668-48da-9866-75be8bc86f4d",
    "rssi": -52,
    "clientTimestamp": "2026-09-22T00:00:00Z"
  }
  ```
  The server calculates:
  $$\text{distance} = 10^{\frac{A - \text{RSSI}}{10 \cdot n}}$$
  If `rssi >= beacon.rssi_cutoff` (e.g. `-52 >= -75`), the status is set to `"present"`.
- **Attack Vector**:
  An absent student on another floor, in their dorm room, or anywhere on the campus LAN can execute:
  ```bash
  curl -X POST http://<server-ip>:3000/checkin \
    -H "Content-Type: application/json" \
    -d '{"studentId":"ABSENT_STUDENT","beaconUuid":"8ec76ea3-6668-48da-9866-75be8bc86f4d","rssi":-45}'
  ```
  The server will return `201 Created` with `status: "present"`, recording attendance for someone who never attended class.
- **Remediation**:
  1. *Immediate*: Implement cryptographic nonces generated by the classroom beacon (see VULN-02).
  2. *Architectural*: Have the beacon rotate an Ephemeral ID (EID) or Time-based One-Time Password (TOTP) every 30–60 seconds, which the server validates against a shared secret.

#### VULN-02: Static & Unencrypted BLE Beacon (Trivial Cloning)
- **Severity**: **HIGH** (CVSS: 7.5)
- **Affected File**: `esp32-beacon/PACBAS_Beacon.ino`
- **Technical Analysis**:
  The ESP32 broadcasts a fixed standard iBeacon packet:
  - Apple Company ID: `0x4C00`
  - Proximity UUID: `8ec76ea3-6668-48da-9866-75be8bc86f4d`
  - Major: `101`, Minor: `1`, TxPower: `-59`
- **Attack Vector**:
  iBeacon advertising packets are completely unencrypted and non-connectable. Any student with the free Android/iOS app **nRF Connect** or another ESP32 can inspect the beacon once, copy its UUID/Major/Minor, and broadcast the exact same iBeacon signal from their own phone or laptop anywhere on campus.
- **Remediation**:
  - Migrate from static iBeacon to an **Ephemeral ID (EID)** or dynamic advertisement payload.
  - Compute a rolling HMAC hash:
    $$\text{Payload} = \text{HMAC-SHA256}(K_{\text{room}}, \lfloor \text{UnixTime} / 30 \rfloor)$$
  - The Android app forwards this rolling token to the backend, and the backend verifies it against its own clock and $K_{\text{room}}$.

#### VULN-03: Complete Absence of Authentication & Authorization
- **Severity**: **CRITICAL** (CVSS: 9.1)
- **Affected File**: `backend/server.js`, `backend/routes/checkin.js`
- **Technical Analysis**:
  No API authentication middleware exists. There are no API keys, JWTs, bearer tokens, or session cookies.
- **Attack Vector**:
  Any client capable of reaching port 3000 can invoke any API endpoint. An attacker can write a script to register thousands of fake students or corrupt existing logs.
- **Remediation**:
  - Implement JWT-based student session authentication.
  - Require a Bearer token in the `Authorization` header for all requests to `/checkin`.

---

#### VULN-04: "Buddy Punching" (Arbitrary Student ID Submission)
- **Severity**: **HIGH** (CVSS: 7.5)
- **Affected File**: `android-app/.../MainActivity.kt`, `backend/routes/checkin.js`
- **Technical Analysis**:
  The student ID is an unvalidated, editable text string in `editStudentId`.
- **Attack Vector**:
  One student present in the classroom can simply enter their classmate's ID into their app, tap "Check In", change the ID to another classmate, and repeat.
- **Remediation**:
  - Hardware Fingerprinting / Keystore Binding: Generate an asymmetric key pair inside the Android Hardware-Backed Keystore (`KeyGenParameterSpec`) during enrollment. The public key is registered to the student's account.
  - Android `BiometricPrompt`: Require fingerprint or face authentication immediately prior to transmitting the check-in request.

---

#### VULN-05: Cleartext HTTP Transmission (`usesCleartextTraffic="true"`)
- **Severity**: **HIGH** (CVSS: 7.4)
- **Affected File**: `android-app/app/src/main/AndroidManifest.xml` (line 30), `backend/server.js`
- **Technical Analysis**:
  The application explicitly enables cleartext traffic:
  ```xml
  android:usesCleartextTraffic="true"
  ```
  The network traffic uses `http://` over unencrypted TCP port 3000.
- **Attack Vector**:
  Any user on the shared Wi-Fi can run `tcpdump` or Wireshark and sniff student IDs, timestamps, and beacon UUIDs, or alter requests in-flight via ARP spoofing.
- **Remediation**:
  - Enforce TLS 1.3 (`https://`).
  - Implement certificate pinning (or trust local custom CA certificates in testing) and set `android:usesCleartextTraffic="false"`.

---

#### VULN-06: Replay Attacks & Untrusted Client Timestamps
- **Severity**: **MEDIUM** (CVSS: 6.5)
- **Affected File**: `backend/routes/checkin.js` (lines 13, 34)
- **Technical Analysis**:
  The server accepts `clientTimestamp` without requiring a cryptographic nonce, counter, or signature.
- **Attack Vector**:
  An attacker captures a valid check-in request from yesterday and replays it today.
- **Remediation**:
  - Reject requests where `abs(now - clientTimestamp) > 60` seconds.
  - Require a server-issued challenge nonce or rolling beacon token that expires within 30 seconds.

---

#### VULN-07: Lack of Rate Limiting & Denial of Service (DoS)
- **Severity**: **MEDIUM** (CVSS: 5.3)
- **Affected File**: `backend/server.js`, `backend/routes/checkin.js`
- **Technical Analysis**:
  No rate-limiting middleware (`express-rate-limit`) is configured.
- **Attack Vector**:
  A single device can send 10,000 requests per minute to `POST /checkin`, locking the SQLite database file (`pacbas.db`) and causing memory exhaustion.
- **Remediation**:
  - Add `express-rate-limit`: limit each IP and each `studentId` to 5 requests per minute.
  - Add SQLite database indexing and connection pool controls.

---

#### VULN-08: RF Signal Bleed & Boundary Inaccuracy
- **Severity**: **MEDIUM** (CVSS: 5.0)
- **Affected Component**: ESP32 RF / BLE Hardware Layer
- **Technical Analysis**:
  At 2.4 GHz, BLE signals penetrate drywall, thin partitions, and glass windows. With a cutoff of `-75 dBm`, an ESP32 placed near a door will allow students standing in the adjacent corridor or bathroom to register as "present".
- **Remediation**:
  - Calibrate beacon placement: Mount the ESP32 in the center of the ceiling rather than near doors or windows.
  - Set hardware attenuation: Lower ESP32 transmit power via `esp_ble_tx_power_set(ESP_BLE_PWR_TYPE_ADV, ESP_PWR_LVL_N12)` to physically constrain radiation range.
  - Implement dynamic OTP challenges on the classroom whiteboard or projector.

---

#### VULN-09: Information Disclosure in `/checkin/history`
- **Severity**: **MEDIUM** (CVSS: 5.3)
- **Affected File**: `backend/routes/checkin.js` (lines 47–53)
- **Technical Analysis**:
  `GET /checkin/history` returns the last 200 attendance records, exposing student IDs, presence statuses, and timestamps to any anonymous client on the network.
- **Remediation**:
  - Restrict `/checkin/history` behind instructor/admin role authentication.
  - Ensure students can only query their own records using their authenticated session.

---

#### VULN-10: Wildcard CORS Configuration
- **Severity**: **LOW** (CVSS: 4.3)
- **Affected File**: `backend/server.js` (line 7)
- **Technical Analysis**:
  `app.use(cors())` sets `Access-Control-Allow-Origin: *`.
- **Remediation**:
  - Restrict CORS origin to designated dashboard domains or disable CORS if accessed strictly by native apps and local dashboards.

## PART 2: ESP32 Setup & Architecture Deep-Dive

### Hardware Specifications
- **Module**: ESP32-WROOM-32 (38-pin or 30-pin DevKit V1)
- **Microcontroller**: Dual-core Tensilica Xtensa 32-bit LX6, 240 MHz
- **Wireless**: 2.4 GHz Wi-Fi (802.11 b/g/n) and Bluetooth v4.2 BR/EDR & BLE
- **Power**: 5V micro-USB or 3.3V regulated rail

### Firmware Architecture (`PACBAS_Beacon.ino`)

The firmware implements a **non-connectable, pure advertiser** (`ADV_TYPE_NONCONN_IND`). It does not establish BLE connections, handle pairing, or accept incoming scan requests, which maximizes airtime efficiency and eliminates connection exhaustion denial of service.

```
+-------------------------------------------------------------+
|                      ESP32 Firmware                         |
|                                                             |
|  +------------------------+      +-----------------------+  |
|  |   Setup Phase          | ---> |   Fast Adv (100ms)    |  |
|  |   Initialize BLEDevice |      |   First 30 Seconds    |  |
|  +------------------------+      +-----------------------+  |
|                                              |              |
|                                              v              |
|                                  +-----------------------+  |
|                                  |  Steady Adv (350ms)   |  |
|                                  |  Low-Power Operation  |  |
|                                  +-----------------------+  |
+-------------------------------------------------------------+
```

#### iBeacon Packet Anatomy (25 Bytes Payload)

```
Offset  Length  Field                  Value / Description
----------------------------------------------------------------------------------
0x00    1 byte  Length                 0x1A (26 bytes total)
0x01    1 byte  Type                   0xFF (Manufacturer Specific Data)
0x02    2 bytes Company Identifier     0x4C00 (Apple Inc. - Little Endian)
0x04    1 byte  Beacon Type            0x02 (iBeacon)
0x05    1 byte  Beacon Length          0x15 (21 bytes)
0x06   16 bytes Proximity UUID         8ec76ea3-6668-48da-9866-75be8bc86f4d
0x16    2 bytes Major Number           0x0065 (101 - e.g. Building / Floor)
0x18    2 bytes Minor Number           0x0001 (1 - e.g. Classroom ID)
0x1A    1 byte  Measured Power (1m)    0xC5 (-59 dBm, two's complement)
```

#### Advertising Interval Strategy
- **Fast Discovery Phase (`ADV_INTERVAL_FAST_MS = 100ms`)**: For the first 30 seconds after boot (`FAST_PHASE_SECONDS = 30`), the beacon broadcasts every 100ms (160 units $\times 0.625\text{ms}$). This guarantees rapid discovery when students walk in.
- **Steady-State Phase (`ADV_INTERVAL_SLOW_MS = 350ms`)**: Reduces channel congestion and power consumption while remaining within the Android BLE scan window.

### Step-by-Step Flashing & Setup Guide

#### 1. Arduino IDE Configuration
1. Open Arduino IDE (v2.x recommended).
2. Go to **File → Preferences → Additional Boards Manager URLs**:
   ```
   https://raw.githubusercontent.com/espressif/arduino-esp32/gh-pages/package_esp32_index.json
   ```
3. Go to **Tools → Board → Boards Manager**, search for `esp32`, and install **esp32 by Espressif Systems**.
4. Select **Tools → Board → ESP32 Arduino → ESP32 Dev Module**.
5. Set the parameters:
   - **Upload Speed**: `921600` (or `115200` if upload fails)
   - **CPU Frequency**: `240MHz`
   - **Flash Frequency**: `80MHz`
   - **Partition Scheme**: `Default 4MB with spiffs`
   - **Port**: Select the USB Serial port (`/dev/ttyUSB0` on Linux, `COM3` on Windows, `/dev/cu.usbserial` on macOS).

#### 2. Per-Room Configuration
Before uploading, customize the constants at the top of `PACBAS_Beacon.ino`:
```cpp
#define ROOM_UUID          "8ec76ea3-6668-48da-9866-75be8bc86f4d" // Unique per physical beacon
#define ROOM_MAJOR         101      // Floor or building identifier
#define ROOM_MINOR         1        // Room number
#define MEASURED_POWER     -59      // Calibrated RSSI at 1 meter
#define DEVICE_NAME        "PACBAS-Beacon-101-1"
```

#### 3. Upload & Serial Verification
1. Click **Upload** (Hold the `BOOT` button on the ESP32 board if the serial connection stalls at `Connecting......._____`).
2. Open the **Serial Monitor** at **115200 baud**.
3. Confirm boot output:
   ```text
   === PACBAS Beacon starting ===
   Room UUID:  8ec76ea3-6668-48da-9866-75be8bc86f4d
   Major/Minor: 101 / 1
   Measured Power (A @ 1m): -59 dBm
   Advertising started (fast discovery phase).
   [heartbeat] uptime=10s, advertising...
   Switched to steady-state advertising interval (350ms).
   ```

### Calibration: Log-Distance Path Loss Model

The backend and Android client compute proximity using the Log-Distance Path Loss Model:

$$d = 10^{\frac{A - \text{RSSI}}{10 \cdot n}}$$

- **$A$ (`MEASURED_POWER`)**: Expected RSSI at exactly 1 meter distance. Default: `-59 dBm`.
- **$\text{RSSI}$**: Trimmed-mean signal strength measured by the smartphone receiver.
- **$n$ (`PATH_LOSS_EXPONENT`)**: Propagation exponent determined by physical environment:
  - **$n = 2.0$**: Free space / line-of-sight outdoors.
  - **$n = 2.7 - 3.2$**: Standard classroom with desks, chairs, and moderate multipath reflection.
  - **$n = 3.5 - 4.5$**: Heavy concrete walls, metal dividers, dense obstruction.

#### Practical Calibration Protocol:
1. Place the ESP32 in its intended mounting location (recommended: centered on ceiling, 2.5m elevation).
2. Stand exactly 1.0 meter away with the test phone at chest height.
3. Collect 30 consecutive RSSI readings using the app or nRF Connect.
4. Drop the 3 highest and 3 lowest readings; compute the average of the remaining 24 readings.
5. Set `MEASURED_POWER` in `PACBAS_Beacon.ino` and `reference_rssi_a` in `db.js` to this value.
6. Stand at the classroom doorway (desired boundary), record RSSI, and set `rssi_cutoff` (e.g. `-75 dBm`) so anyone past the door falls into `"rejected_out_of_range"`.

## PART 3: Security Hardening Roadmap

### Phase 1: MVP Hardening (Immediate)
1. **Dynamic Backend Configuration**: Allow entering the server URL in the app UI, avoiding hardcoded LAN IPs.
2. **Strict Backend Input Validation**: Sanitize `studentId`, enforce integer RSSI between `-100` and `0`, reject `NaN` or `Infinity`.
3. **Database Constraints**: Prevent duplicate check-in spam from the same student within a 15-minute window.
4. **Rate Limiting**: Protect `/checkin` with IP and ID rate limiting.

### Phase 2: Production Anti-Cheat Architecture
1. **Rolling Ephemeral Beacon (AES-128 / HMAC)**:
   - ESP32 increments a counter or uses an onboard RTC.
   - Computes a dynamic 4-byte rolling token every 30 seconds:
     $$\text{Token} = \text{Truncate}(\text{HMAC}(K_{\text{secret}}, \text{Floor}(\text{Time}/30)))$$
   - Broadcasts the token in the Major/Minor or Service Data field.
   - The backend validates that the token matches the current time window before approving check-in.
2. **Hardware-Backed Device Fingerprint**:
   - Generate an Android Keystore private key on first app enrollment.
   - Sign check-in payloads: $\text{Sign}_{K_{\text{device}}}(\text{StudentID} \parallel \text{Nonce} \parallel \text{Timestamp})$.
3. **Biometric Authentication**:
   - Require Android `BiometricPrompt` prior to dispatching check-in.
4. **TLS 1.3 & Certificate Pinning**:
   - Enforce HTTPS and disable cleartext traffic.
